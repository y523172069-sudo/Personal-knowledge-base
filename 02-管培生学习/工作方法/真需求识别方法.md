# 真需求识别方法

## 核心问题

收到一个任务时，不先问“我要做什么材料”，而是先问：**这个任务最终要帮助谁完成什么事情？**

## 六步检查

1. **目标用户**：谁会使用结果，谁会受到影响？
2. **真实场景**：用户现在如何完成这件事，痛点发生在哪里？
3. **业务目标**：公司希望改变什么结果，而不只是交付什么文档？
4. **验证标准**：什么事实能够证明问题被解决？
5. **成本约束**：用户提交、业务审核和研发实现分别需要付出什么成本？
6. **最小范围**：在当前周期内，最小可以验证的交付是什么？

## 真需求三层判断法

产品轮岗课题后，当前方法可以进一步收敛为三层判断：

| 层级 | 核心问题 | 作用 |
| --- | --- | --- |
| 业务结果判断 | 如果这个需求不做，会影响什么业务结果？ | 判断是否值得继续关注 |
| 核心目标判断 | 这个需求到底服务哪个核心目标？ | 判断方向是否清楚 |
| 价值验证判断 | 做完以后怎么证明它有效？ | 判断是否能复盘产研投入 |

当前阶段对“真需求”的定义：

> 真需求 = 解决真实问题 + 服务核心目标 + 产生可验证业务结果。

常见错误是把“功能诉求”直接当作“需求”。例如“增加评价链接”只是表层动作，背后可能是客户反馈收集不完整、服务质量难评估或流程问题无法发现。

## P0 / P1 / P2 判断

优先级不是业务方说了算，也不是产品经理凭感觉判断，而应是三层判断后的输出：

| 类型 | 判断标准 |
| --- | --- |
| P0 真需求 | 战略相关、影响范围大、业务结果强，且通常是管理层重点关注事项 |
| P1 真需求 | 问题真实、目标明确、价值较强，但未达到公司级战略优先级 |
| P2 优化需求 | 问题真实，但影响范围较小，更多是局部流程或体验优化 |
| 待验证需求 | 业务结果、核心目标或验证指标不清楚，需要继续调研 |
| 暂缓需求 | 当前价值不足、影响有限或投入产出不匹配 |

## 需求池描述模板

在需求池阶段，为了让产品经理、Leader 和相关协作方快速判断需求价值，可以统一描述字段：

```text
【需求背景】
【当前问题】
【目标对象】
【需求内容】
【当前阶段】
【待确认事项】
【下一步动作】
```

目标字段可以用：

```text
目标 = 价值方向 + 衡量指标 + 目标变化 + 对比方式
```

这套模板的目的不是让文档更好看，而是让需求更容易被判断、推进和复盘。

## 小联盟调研中的应用

```text
原始任务：调研行业资质与认证
        ↓
重新追问：产品为什么需要这些资质？
        ↓
核心目标：验证货代企业真实存在的业务优势
        ↓
用户约束：多数中小型货代难以提供高门槛证书
        ↓
方案调整：优先采用 AWB、合作协议、签收证明等履约材料
```

## 关于“大课题不够落地”的责任边界

公司可能给出一个过大的命题，但个人仍需要对方案范围负责。两者需要区分：

- **命题责任**：公司或导师决定为什么研究这个方向；
- **范围责任**：执行者决定本周期具体解决哪个用户、哪个场景、哪个环节，以及用什么结果验证。

因此，“公司给的课题太大”可以解释约束，但不能完全否定“不够落地”的反馈。更有效的处理方式是主动把大题拆成一个可验证的小问题，并在汇报开头明确本次不解决什么。

## Jira 小需求中的应用

| 表层需求 | 背后问题 | 真实目标 | 可验证指标 |
| --- | --- | --- | --- |
| 增加工单评价链接 | 客户反馈收集不完整 | 完善客户反馈闭环，发现流程问题 | 评价覆盖率、反馈数量、差评处理率 |
| 调整风险订阅上限数字 | 商业化权益与页面展示不一致 | 保证权益承诺、销售口径和网页展示一致 | 页面一致性检查、销售反馈 |
| 取消不必要审批通知并统一币种 | 内部流程通知干扰、金额口径不统一 | 提高审批效率，降低理解成本 | 通知数量、审批处理效率、异常反馈 |
