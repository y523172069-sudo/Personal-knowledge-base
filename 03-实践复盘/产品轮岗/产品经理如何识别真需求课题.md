# 产品经理如何识别真需求课题

## 1. 背景

产品轮岗期间，课题最初被拆成三条线：

| 主线 | 要搞清楚的问题 | 预期产出 |
| --- | --- | --- |
| 需求管理 | 产品经理如何接收、判断、拒绝、推进、验证需求 | 一套需求流转 SOP |
| 商业化产品 | 商业化产品如何从客户需求变成产品权益和收入 | 一个商业化产品分析框架 |
| AI 提效 | AI 如何帮助产品经理提高调研、分析、文档、原型效率 | 一套 AI 辅助产品工作的场景清单 |

后续课题收敛到“产品经理如何识别真需求”。这个收敛是必要的：原始范围过大，如果同时覆盖需求管理、商业化产品和 AI 提效，很难在短周期内形成可落地结论。

## 2. 问题定义

产品经理在需求池阶段面对的不是完整需求，而是来自会议、聊天记录、业务反馈、上级任务、销售和风控问题中的零散诉求。

这些诉求可能表现为：

- 增加一个字段；
- 优化一个工单；
- 调整一个数字；
- 增加评价链接；
- 完善一个流程；
- 建立一个方向性项目。

如果产品经理只是把功能诉求直接转成方案，容易出现“功能做了，但没有真正解决业务问题，也无法证明价值”的问题。

因此，本课题的核心问题是：

> 产品经理如何在需求池阶段判断一个需求是不是真需求、是否值得继续推进、做完以后如何验证价值。

## 3. 真需求定义

当前阶段的定义：

> 真需求 = 解决真实问题 + 服务核心目标 + 产生可验证业务结果。

需要区分两点：

- 真需求不等于功能诉求。业务方说“我要一个功能”，产品经理要还原它背后的问题；
- 真需求不等于 P0。一个需求可能是真实问题，但不一定是最高优先级。

## 4. 真需求三层判断法

### 第一层：业务结果判断

先问：

> 如果这个需求不做，会影响什么业务结果？

可从三个方向判断：

| 判断方向 | 说明 |
| --- | --- |
| 客户信任 | 是否影响客户对平台能力、服务保障、风控权益的信任 |
| 销售效率 | 是否影响销售跟进、客户判断、成交辅助信息获取 |
| 协作成本 | 是否导致销售、风控、客成、产品之间反复沟通和重复确认 |

这一层用于判断需求是否值得继续关注。

### 第二层：核心目标判断

继续问：

> 这个需求到底服务哪个核心目标？

当前可先收敛为三类目标：

| 核心目标 | 示例 |
| --- | --- |
| 客户信任建设 | 认证资质、平台背书、风控保障、服务能力展示 |
| 成交转化增长 | 会员购买、询盘转化、续费、增值服务成交 |
| 销售效率提升 | 帮助销售更快判断客户价值、获取成单辅助信息 |

这一层用于判断需求方向是否清楚。

### 第三层：价值验证判断

最后问：

> 做完以后怎么证明它有效？

| 目标类型 | 可验证指标 |
| --- | --- |
| 客户信任建设 | 客户评价数量、评价覆盖率、客户对权益反馈、续费反馈 |
| 成交转化增长 | 会员购买数量、增值服务成交数量、收入、询盘转化 |
| 销售效率提升 | 沟通次数减少、资料查找时间减少、成单辅助信息完整度提升 |

这一层用于避免“上线即结束”，要求需求能够被复盘。

## 5. P0 / P1 / P2 是判断后的输出

P0 / P1 / P2 不应只由业务方或主观感受决定，而应是三层判断后的结果：

| 类型 | 判断标准 |
| --- | --- |
| P0 真需求 | 战略相关、影响范围大、业务结果强，且通常是管理层重点关注事项 |
| P1 真需求 | 问题真实、目标明确、价值较强，但未达到公司级战略优先级 |
| P2 优化需求 | 问题真实，但影响范围较小，更多是局部流程或体验优化 |
| 待验证需求 | 业务结果、核心目标或验证指标不清楚，需要继续调研 |
| 暂缓需求 | 当前价值不足、影响有限或投入产出不匹配 |

这套判断不是为了打标签，而是为了形成处理结论：进入方案设计、继续调研、调整优先级或暂缓。

## 6. 需求池字段规范优化

课题中进一步识别出，需求池不是简单存放任务，而是需求责任链路管理工具。

### 6.1 需求池的核心价值

需求池的价值是让需求从“零散沟通”变成“可记录、可判断、可跟踪、可复盘”的管理对象。

它需要回答：

- 谁提出；
- 谁判断；
- 谁负责；
- 谁实现；
- 谁关注结果；
- 当前阶段是什么；
- 下一步该由谁处理。

### 6.2 需求阶段标记

不是所有需求都应该用同一个完整度标准判断。早期方向任务和待开发需求应区分阶段：

| 需求阶段 | 含义 |
| --- | --- |
| 方向任务 | 来自 CEO / Leader 的方向性任务，尚未明确具体需求 |
| 立项中 | 已确认要研究，但仍在调研和梳理目标 |
| 待补充 | 需求内容不完整，需要补充背景、规则、数据或协作意见 |
| 待评估 | 信息基本完整，等待判断是否推进 |
| 待开发 | 已形成明确产品方案，可以进入研发 |
| 开发中 | 研发已介入 |
| 已上线 | 功能已发布 |
| 已关闭 | 需求已完成、取消、合并或不再推进 |

### 6.3 描述字段模板

用于解决“需求说不清楚”的问题：

```text
【需求背景】
【当前问题】
【目标对象】
【需求内容】
【当前阶段】
【待确认事项】
【下一步动作】
```

### 6.4 目标（量化）字段模板

用于解决“价值说不清楚”的问题：

```text
目标 = 价值方向 + 衡量指标 + 目标变化 + 对比方式
```

价值方向可包括：

| 价值方向 | 可写指标 |
| --- | --- |
| 提效 | 处理时间减少、查找时间减少、沟通次数减少 |
| 人效 | 单人可处理任务数提升、重复工作减少 |
| 工作节奏 | 截止时间更明确、状态同步更及时、延期任务减少 |
| 客户体验 | 客户反馈数量增加、评价覆盖率提升、投诉减少 |
| 风险控制 | 漏处理减少、审批链路清晰、异常任务识别率提升 |
| 管理效率 | Leader 判断需求价值时间减少、高价值需求识别更快 |

## 7. 案例验证：风控工单优化

以风控工单优化为例，表层动作可能是“增加工单评价链接”，但背后目标可能是完善客户反馈闭环，判断服务质量，发现流程问题。

| 层级 | 示例 |
| --- | --- |
| 表层需求 | 增加工单评价链接 |
| 背后问题 | 客户反馈收集不完整 |
| 真实目标 | 判断服务质量，发现流程问题 |
| 价值指标 | 评价覆盖率、反馈数量、差评处理率 |
| 当前判断 | 待验证需求 / P1 候选真需求 |

这个案例的关键不是马上判断高优先级，而是先补充客户反馈、高频痛点和评价数据，再决定是否进入后续方案设计。
